Learn the theory

Four properties.
One reliable transaction.

Understand the database guarantees behind the simulator and where each concept appears in the implementation.

4 pillarsDatabase reliability
A.

Atomicity

ALL OR NOTHING

A transaction's changes are treated as one unit. If an operation fails before commit, rollback undoes the uncommitted changes.

In this simulator

The transfer starts a transaction, debits the sender, and can be intercepted. The original transaction is rolled back and a failed-attempt record is written separately.

Key operations: start_transaction(), commit(), rollback().

C.

Consistency

VALID STATES

A transaction must preserve the database's defined integrity rules, moving it from one valid state to another.

In this simulator

Positive transfer amount and different accounts are validated by the app. A MySQL CHECK constraint such as balance >= 0 can reject a negative account balance.

Key ideas: input validation, constraints and error handling.

I.

Isolation

CONCURRENT WORK

Concurrent transactions should not interfere in ways that violate the database's isolation guarantees.

In this simulator

The desktop version used a short application buffer and MySQL SELECT ... FOR UPDATE row locks. This website accepts overlapping transfer requests through the Flask API. MySQL coordinates conflicting updates with row locks.

Key ideas: concurrent transactions, locks and isolation levels.

D.

Durability

PERSIST AFTER COMMIT

After a successful commit, changes should survive failures covered by the database's durability guarantees.

In this simulator

The Python project reconnects to MySQL and checks that a committed transaction record remains available. Committed changes are saved in the configured MySQL database.

Key operations: commit, persistent storage and verification.

Test the consistency constraint

Ask MySQL to reject an account with a negative balance.

What happens in a bank transfer?

Begin transaction

Create a transaction record, validate accounts and lock rows that need protection.

Apply both sides

Debit the sender and credit the receiver inside the same transaction.

Commit or roll back

Commit only when the transfer is complete. Otherwise roll back the uncommitted changes.

Verify and log

Store transaction status and timestamps so the lifecycle can be inspected later.

Using the simulator

Choose the sender and receiver

Select two different sample accounts. The same account cannot send money to itself.

Enter a positive amount

Use a positive number no greater than the sender's available balance.

Start multiple transfers

Submit another transfer while an earlier one is running. Each demo transfer has its own timer and lifecycle.

Inspect or export

Check timestamps and statuses in Transaction Activity, open details, or export the session as CSV.

Project objective

To demonstrate how ACID properties support reliable database transactions through an approachable interface, transaction logs, examples and practice questions.

Technology direction

The web app uses Python, Flask, MySQL Connector and MySQL. The server performs each transfer in a database transaction; MySQL row locks coordinate concurrent requests.
